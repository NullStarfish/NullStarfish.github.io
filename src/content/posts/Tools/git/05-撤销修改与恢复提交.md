Git 的“撤销”可能指恢复文件、取消暂存、移动分支或新增一个反向提交。执行前必须先确定
要改变的是工作区、index 还是提交历史。

---

### 一、丢弃工作区修改

```bash
git restore path/to/file
git restore --source=HEAD -- path/to/file
```

它会用 index（或指定 source）的内容覆盖工作区，未提交修改通常无法恢复。先用
`git diff` 确认目标。

---

### 二、取消暂存

```bash
git restore --staged path/to/file
```

这会让 index 恢复为 `HEAD` 中的版本，但保留工作区修改。等价的传统写法是：

```bash
git reset HEAD -- path/to/file
```

---

### 三、Reset 移动当前分支

```bash
git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1
```

| 模式 | 移动 branch | 重置 index | 重置工作区 |
| :--- | :---: | :---: | :---: |
| `--soft` | 是 | 否 | 否 |
| `--mixed` | 是 | 是 | 否 |
| `--hard` | 是 | 是 | 是 |

`--hard` 会丢弃已跟踪文件的未提交修改。不要仅因为工作区“看起来乱了”就执行它。

---

### 四、Revert 适合共享历史

```bash
git revert COMMIT
git revert -m 1 MERGE_COMMIT
```

revert 不移动旧提交，而是创建一个效果相反的新提交，因此适合已经 push 的历史。revert
merge commit 时，`-m` 指定要保留的 mainline parent，执行前必须确认父提交含义。

---

### 五、用 Reflog 找回提交

branch 被 reset、rebase 或误删后，提交对象通常不会立刻消失：

```bash
git reflog --date=local
git show HEAD@{2}
git branch rescue COMMIT_ID
```

reflog 是本地引用移动日志，不会随 push 共享，也不是永久备份。发现误操作后尽快创建
branch 或 tag 固定目标提交。

---

### 六、推荐决策顺序

1. `git status` 和 `git diff` 确认变化位于哪一层。
2. 未提交文件用 `restore`；取消暂存用 `restore --staged`。
3. 本地未共享历史可以谨慎 `reset`。
4. 已共享历史优先 `revert`。
5. 引用已经移动时检查 `reflog`。
