tag 是通常不移动的引用，适合给发布提交命名。可靠工作流的重点不是记住最多命令，而是
在每个会改变状态的步骤前后进行检查。

---

### 一、Lightweight 与 Annotated Tag

```bash
git tag temp-mark
git tag -a v1.2.0 -m "Release v1.2.0"
```

lightweight tag 只是一个引用；annotated tag 是独立对象，包含创建者、时间和说明，更适合
正式发布。

查看和验证：

```bash
git tag --list 'v1.*' --sort=-version:refname
git show v1.2.0
git tag -v v1.2.0
```

`tag -v` 只适用于带受支持签名的 tag，并要求本机具有对应公钥和验证工具。

---

### 二、推送 Tag

普通 `git push` 默认不推送所有 tag：

```bash
git push origin v1.2.0
git push origin --tags
```

删除错误 tag 需要同时处理本地和远程：

```bash
git tag -d v1.2.0
git push origin :refs/tags/v1.2.0
```

已经公开的版本 tag 应视为不可变；需要修复时发布新版本号，避免不同用户的同名 tag 指向
不同提交。

---

### 三、开始任务

```bash
git switch main
git fetch origin --prune
git merge --ff-only origin/main
git switch -c feature/topic
```

这组命令明确区分下载和整合步骤，也保证功能分支从已知的最新主线开始。

---

### 四、提交前检查

```bash
git status --short
git diff
git add -p
git diff --cached
# 运行项目测试和格式检查
git commit
git show --stat HEAD
```

不要用 `git add .` 掩盖自己不知道改了什么。配置、生成文件、大二进制和密钥都应在提交
前被明确识别。

---

### 五、同步并提交评审

```bash
git fetch origin
git rebase origin/main
# 重新运行测试
git push -u origin feature/topic
```

代码评审后新增修复提交，或在团队允许时用交互式 rebase 整理自己的分支。若历史已经被
重写，使用 `git push --force-with-lease`，并再次确认没有覆盖他人提交。

---

### 六、发布前检查清单

1. 工作区干净，测试通过。
2. `HEAD` 是计划发布的提交。
3. 版本号、变更记录和构建产物一致。
4. 创建 annotated tag，并检查 `git show TAG`。
5. 先推送提交，再推送指定 tag。
6. 从远程或干净 clone 验证发布可复现。
