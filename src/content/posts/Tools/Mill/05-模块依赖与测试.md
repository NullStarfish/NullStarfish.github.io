Mill 中的 module 同时承担两个职责：它是命令行上的命名空间，也是共享一组任务和配置
的构建单元。不要直接把 RTL 层次结构一比一转换为 Mill module；只有需要独立编译、
测试、依赖或缓存边界时，才值得拆成构建模块。

---

### 一、用 trait 集中公共配置

```scala
package build
import mill.*
import mill.scalalib.*

trait ChiselModule extends ScalaModule {
  def scalaVersion = "2.13.18"
  def chiselVersion = "7.7.0"

  override def mvnDeps = Seq(
    mvn"org.chipsalliance::chisel:$chiselVersion"
  )

  override def scalacPluginMvnDeps = Seq(
    mvn"org.chipsalliance:::chisel-plugin:$chiselVersion"
  )
}
```

以后升级版本或增加统一编译选项，只需要修改 trait。具体模块仍可以继续 `override`。

---

### 二、声明模块之间的编译依赖

```scala
object common extends ChiselModule

object core extends ChiselModule {
  override def moduleDeps = Seq(common)
}

object soc extends ChiselModule {
  override def moduleDeps = Seq(common, core)
}
```

运行 `mill soc.compile` 时，Mill 会先保证 `common.compile` 和 `core.compile` 有效，并把
上游编译产物加入下游 classpath。`moduleDeps` 是 Scala/JVM 构建依赖，不等同于
Verilog 模块例化关系。

---

### 三、测试是嵌套子模块

```scala
trait ChiselModule extends ScalaModule {
  // 公共配置略

  object test extends ScalaTests with TestModule.ScalaTest {
    override def mvnDeps = Seq(
      mvn"org.scalatest::scalatest::3.2.19"
    )
  }
}
```

于是每个具体模块都得到 `common.test`、`core.test` 等任务。测试模块会继承或关联主模块
的编译结果，并使用自己的测试源码与依赖。

---

### 四、模块目录决定默认源码位置

Mill 的模块路径、源码目录、命令和 `out/` 路径通常互相对应。例如 `core` 模块默认从
自己的 `moduleDir` 下寻找源码。若代码仍集中在仓库根目录，可采用三种策略：

1. 使用 `SbtModule` 并调整 `moduleDir`，适合标准单体项目。
2. 覆写 `sources`/`generatedSources`，显式选取源文件。
3. 重构物理目录，让每个构建模块拥有自己的源码树。

第三种长期最清晰，但会影响源码组织；第二种适合在不改工程目录的情况下为某个单元建立
快速测试边界。
