链接成功只说明 ld 能生成输出文件，不代表内存布局一定符合硬件和启动代码预期。
调试链接脚本时，应同时检查 section、segment、symbol 和原始镜像。

---

### 一、始终生成 Map 文件

```bash
ld -T link.ld -Map=app.map -o app.elf *.o
```

通过 GCC driver：

```bash
gcc -T link.ld -Wl,-Map=app.map -o app.elf *.o
```

Map 文件可以回答：

- 每个输入 section 被放进哪个输出 section。
- 每个输出 section 的地址和大小。
- archive 中哪个 member 因哪个符号被抽取。
- linker symbol 的最终值。
- 哪些 section 被丢弃。

---

### 二、检查 Section

```bash
readelf -S app.elf
objdump -h app.elf
```

重点检查：

- `.text`、`.data`、`.bss` 的地址、大小和 alignment。
- `ALLOC`、`LOAD`、`CODE`、`DATA` 等 flag。
- VMA 和 LMA 是否符合预期。
- 是否出现没有被脚本接住的 orphan section。

---

### 三、检查 Segment 和入口

```bash
readelf -h app.elf
readelf -l app.elf
```

ELF header 中检查 `Entry point address`。Program header 中检查：

- `LOAD` segment 的 `VirtAddr`、`PhysAddr`。
- `FileSiz` 和 `MemSiz`。
- R/W/X flags。
- `Section to Segment mapping`。

脚本中的 section 地址正确，但 loader 仍然装载错误时，问题经常出在 program header。

---

### 四、检查符号与 relocation

```bash
nm -n app.elf
readelf -s app.elf
readelf -r app.elf
objdump -t app.elf
```

`nm -n` 按地址排序，特别适合检查 `_start`、`_data_start`、`_bss_end`、`_stack_top`
等边界符号。

查找一个符号来自哪里：

```bash
ld --trace-symbol=_start ...
```

---

### 五、检查 section GC

```bash
ld --gc-sections --print-gc-sections ...
```

若入口、向量表或注册表消失，检查：

1. 是否存在从 GC root 到该 section 的 relocation 引用。
2. 是否在脚本中使用了 `KEEP`。
3. `ENTRY` 符号是否正确。
4. 输入段名是否和脚本 pattern 一致。

---

### 六、严格处理 Orphan Section

```bash
ld --orphan-handling=warn ...
ld --orphan-handling=error ...
```

开发阶段推荐 `warn`。脚本稳定后可以考虑 `error`，迫使新增 section 明确归类。

---

### 七、内存使用与交叉引用

```bash
ld --print-memory-usage ...
ld --cref -Map=app.map ...
```

`--print-memory-usage` 依赖脚本中的 `MEMORY` region。`--cref` 在 map 中生成符号交叉
引用表，便于分析谁引用了某个函数或变量。

生成纯 binary 后继续检查：

```bash
objcopy -O binary app.elf app.bin
stat -c '%s bytes' app.bin
hexdump -C app.bin | head
```

如果 VMA/LMA 之间存在巨大空洞，flat binary 可能异常膨胀，应重新检查加载地址布局。

### 推荐排查顺序

```text
app.map
  -> readelf -S / objdump -h
  -> nm -n / readelf -s
  -> readelf -l
  -> objdump -dr
  -> 最终 binary 内容
```
